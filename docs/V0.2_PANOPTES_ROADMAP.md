# DroneWatch V0.2 — Project PANOPTES defeat-chain simulation roadmap

Status date: 9 September 2026. Baseline: V0.1.1, one commit ahead of tag `v0.1.0`.

DroneWatch V0.2 repositions the project from a drone-detection dashboard into an
integrated counter-UAS decision and defeat-chain **simulation** platform, aimed at
reducing sensor-to-defeat latency under complex and saturated threat conditions.

## Scope boundary — read before implementing anything

This project is and remains a software simulation of a command-and-control
decision problem.

It must not contain real weapon-control interfaces, firing commands, guidance
algorithms, real-world aiming coordinates, autonomous lethal targeting, physical
effector-control protocols, or any code capable of operating a weapon.

Effectors are abstract entities (`SIM_LASER`, `SIM_EW`, `SIM_INTERCEPTOR`,
`SIM_OTHER`) carrying only software-simulation attributes: availability, busy
state, queue depth, nominal engagement latency, simulated success probability,
simulated resource cost, simulated cooldown, and compatible threat classes. They
must not carry real-world weapon operating parameters.

The engineering objective is the C2 and decision problem, not a weapon.

## The optimisation question

> Can the system convert many heterogeneous sensor observations into a coherent
> threat picture, and move each legitimate threat through a defensible, auditable
> simulated defeat chain faster than an unaided workflow, even under saturation?

Every milestone below should be justifiable against that sentence. The central
metric is **total sensor-to-defeat latency**, decomposed by stage.

## What V0.1.1 already gives us

- A working ingestion endpoint that accepts arbitrary JSON and never rejects a
  malformed sender.
- Defensive normalisation that refuses to invent detections from narrative text,
  refuses to fabricate confidence, and fails to `UNKNOWN` rather than guessing.
- Durable storage, a read API, a frozen operator dashboard, and 35 tests.

These are not throwaway. The normalisation discipline in particular is exactly
the property a fusion system needs, and it is reused rather than replaced.

## What V0.2 requires that V0.1.1 does not have

| Capability | V0.1.1 | Required |
|---|---|---|
| Sensor modalities | One implicit visual webhook | RADAR, RF, EO, IR, ACOUSTIC, extensible |
| Identity | One row per event | Persistent fused tracks across sensors |
| Correlation | None | Multi-sensor association into one track |
| Threat reasoning | Fixed state-to-severity map | Assessment with rationale and uncertainty |
| Decision chain | Stops at stored event | Full chain to simulated defeat and audit |
| Authorisation | None | Explicit, auditable human decision boundary |
| Latency | Not measured | Instrumented per stage, first-class output |
| Saturation | One drone assumed | Many simultaneous tracks, backpressure |
| Data | None owned | Seeded synthetic multi-sensor generator |
| Interop | Viso-shaped only | Viso as one adapter; SAPIENT boundary defined |

## Milestones

Ordering differs from the original sketch in one respect. The latency ledger is
built in M1 rather than deferred to a late milestone, because retrofitting
timestamps across a finished pipeline is far more expensive than stamping each
stage as it is written. Latency is the product, not a report bolted on later.

### M0 — Secure and freeze V0.1.1
- **Purpose.** Establish an immutable, tested baseline before any restructuring.
- **Files.** No new code. Tag `v0.1.1`.
- **Tests.** The existing 35 must pass unchanged.
- **Acceptance.** Tag exists; CI green; frontend byte-identical to `v0.1.0`.
- **Dependencies.** None.
- **Risk.** Low.

### M1 — Domain model, observation schema, latency ledger
- **Purpose.** Define the vocabulary everything else speaks. No behaviour change.
- **Files.** `dronewatch/domain/` (`observation.py`, `track.py`, `threat.py`,
  `engagement.py`, `enums.py`, `latency.py`).
- **Tests.** Pure unit tests. Serialisation round-trips. Ledger monotonicity.
- **Acceptance.** A `SensorObservation` can losslessly represent a current Viso
  payload and a SAPIENT `DetectionReport` field-for-field. Existing API unchanged.
  Classification is a distribution, control evidence is separate from identity,
  the two lifecycles are independent, and no simulated engagement is reachable
  without an authorisation record.
- **Dependencies.** M0.
- **Risk.** Medium. Getting this wrong is expensive later, so it is worth
  prototyping against two real message shapes before freezing.

### M2 — Deterministic synthetic scenario generator — COMPLETE
- **Purpose.** Remove the dataset blocker. Everything downstream needs input.
- **Files.** `dronewatch/synthetic/` (`scenario.py`, `generators.py`, `seed.py`),
  `data/synthetic/`.
- **Tests.** Same seed produces byte-identical output. Ground truth is never
  reachable from the observation stream.
- **Acceptance.** MET. Eleven scenarios generate across all five modalities,
  identical output for a given seed, ground truth isolated from observations,
  counterexamples present in both directions, false positives unmarked,
  delay/dropout/duplicate/out-of-order effects present, swarm parameterised,
  CLI working, serialisation byte-identical for a given seed.
- **Dependencies.** M1.
- **Risk.** Medium. Realism is a rabbit hole; kinematics kept deliberately crude.

### M3 — Sensor adapters, Viso demoted to one of many
- **Purpose.** Turn the current normalisation into a pluggable adapter.
- **Files.** `dronewatch/sensors/` (`base.py`, `viso.py`, `synthetic.py`).
- **Tests.** Existing Viso tests re-pointed at the adapter and still passing.
- **Acceptance.** `/webhook/viso` behaviour is bit-for-bit unchanged.
- **Dependencies.** M1, M2.
- **Risk.** Medium. This is the main regression risk in the whole plan.

### M4 — Fused tracks and track management
- **Purpose.** Many observations become one persistent track.
- **Files.** `dronewatch/fusion/` (`association.py`, `manager.py`).
- **Tests.** Association accuracy, fragmentation, loss and reacquisition.
- **Acceptance.** Scenarios D, E, F produce the expected track counts.
- **Dependencies.** M3.
- **Risk.** High. Association is where naive implementations fail first.

### M5 — Threat assessment and prioritisation
- **Purpose.** Rank tracks with stated reasons, not a hidden score.
- **Files.** `dronewatch/threats/`.
- **Tests.** Benign tracks never outrank incursions; every score carries rationale.
  Decoy discrimination evaluated against scenario P.
- **Acceptance.** Scenario B is not prioritised above scenario A. In scenario P,
  measurably fewer simulated effectors are spent on decoys than by a
  discrimination-blind baseline.
- **Note.** Decoy versus threat separation rests on detecting a manoeuvre
  process in the trajectory. See the architecture document. Treat it as a
  hypothesis to be validated, not an assumed capability.
- **Dependencies.** M4.
- **Risk.** Medium.

### M6 — Defeat-chain state machine and authorisation
- **Purpose.** Represent the full chain with an explicit human decision boundary.
- **Files.** `dronewatch/decisions/` (`chain.py`, `authorisation.py`, `audit.py`).
- **Tests.** Illegal transitions rejected. No path reaches simulated engagement
  without a recorded authorisation.
- **Acceptance.** A complete audit record can be reconstructed for any track.
- **Dependencies.** M5.
- **Risk.** Medium.

### M7 — Simulated effector abstraction
- **Purpose.** Model scarcity, contention and cooldown. Nothing more.
- **Files.** `dronewatch/effectors/`.
- **Tests.** Assignment respects availability, cooldown and compatibility.
- **Acceptance.** Under saturation, effector exhaustion is visible rather than silent.
- **Dependencies.** M6.
- **Risk.** Low technically. Requires discipline to keep abstract.

### M8 — Metrics surface
- **Purpose.** Expose what the ledger has been collecting since M1.
- **Files.** `dronewatch/metrics/`, `/api/v2/metrics`.
- **Tests.** Derived stage latencies match hand-computed fixtures.
- **Acceptance.** Every stage in the chain reports a latency.
- **Dependencies.** M6, M7.
- **Risk.** Low.

### M9 — Swarm benchmark harness
- **Purpose.** Make saturation behaviour measurable before optimising anything.
- **Files.** `benchmark.py`.
- **Tests.** Smoke run at small scale in CI; large runs stay out of CI.
- **Acceptance.** `--uas 1|10|50|100` produces comparable latency and backlog curves.
  The harness compares a **per-track workflow against a grouped workflow** across
  increasing simultaneous-track counts, reporting operator decisions required,
  authorisation latency, decision backlog, total sensor-to-simulated-defeat
  latency, false threat actions, simulated resources spent on decoys, legitimate
  threats left unresolved, and throughput. Grouping is not assumed to win.
- **Dependencies.** M8.
- **Risk.** Medium. Benchmarks that measure the harness are a real hazard.

### M10 — Tactical UI integration
- **Purpose.** Unfreeze the frontend only once the data contract is stable.
- **Files.** `index.html` or its successor, plus `/api/v2/*`.
- **Tests.** Presentation-helper tests extended in the existing style.
- **Acceptance.** The defeat chain for a selected track is visible with per-stage timings.
- **Dependencies.** M8.
- **Risk.** Medium.

### M11 — SAPIENT adapter prototype
- **Purpose.** Genuine interoperability, or an honest statement of its absence.
- **Files.** `dronewatch/interop/sapient/`.
- **Tests.** Round-trip against the published protobuf definitions.
- **Acceptance.** Stated as "translates a subset of BSI Flex 335 v2.0
  `DetectionReport`", never as "SAPIENT compliant", unless conformance has
  actually been demonstrated against the standard.
- **Dependencies.** M1, M4.
- **Risk.** High on claims, moderate on code. See the interoperability document.

## Synthetic Data Workstream — REQUIRED

**This is a blocking dependency for most of V0.2 and must not be lost.**

We do not possess a multi-sensor counter-UAS dataset and cannot obtain one from
public sources under a licence that permits this use. Every capability from M4
onward is therefore gated on synthetic data. Treat this as a first-class
workstream with its own milestones, not as test fixtures.

Design rules, in priority order:

1. **Ground truth is separate and never leaks.** Scenario files carry
   `ground_truth_entities[]` and `sensor_observations[]` in distinct namespaces.
   The pipeline under evaluation is handed observations only. Evaluation joins
   the two afterwards. Any import of ground truth into `fusion/`, `threats/`,
   `decisions/` or `effectors/` is a defect, and a test should enforce it.
2. **Reproducible from a seed.** Same seed, same bytes. No wall-clock, no
   unseeded RNG, no set iteration order in output.
3. **Imperfection is the point.** A generator that emits clean observations
   tests nothing. Noise, dropout, duplication, delay, reordering and disagreement
   are required features.
4. **Start crude.** Straight-line kinematics with noise beats a flight dynamics
   model that never ships.

Scenario catalogue to build toward:

| ID | Scenario | Primarily exercises |
|---|---|---|
| A | Single UAS approach | Baseline chain |
| B | Benign / non-threat track | False-alarm discipline |
| C | False positive | Precision |
| D | Sensor disagreement | Fusion conflict handling |
| E | Sensor dropout | Degradation |
| F | Track loss and reacquisition | Continuity, fragmentation |
| G | Sequential incursions | Chain reuse, effector cooldown |
| H | Simultaneous multiple UAS | Concurrency |
| I | Saturation / swarm | Backpressure, operator overload |
| J | Noisy observations | Robustness |
| K | Delayed observations | Late-arrival handling |
| L | Out-of-order observations | Ordering assumptions |
| M | Duplicate observations | Idempotency |
| N | Changing confidence | Assessment stability |
| O | Degraded sensor network | Graceful degradation |
| P | Decoys mixed with real threats | Decoy discrimination, effector husbandry |
| Q | Threat flying a nearly constant route | Counterexample: low manoeuvre, real threat |
| R | Decoy with irregular or tumbling motion | Counterexample: high manoeuvre, not a threat |
| S | Controlled decoy | Counterexample: agency without hostility |
| T | Genuine UAS with weak manoeuvre evidence | Calibration under sparse evidence |
| U | Sensor noise that mimics manoeuvring | False agency evidence |

Evaluation metrics to implement alongside the generator:

- Track association accuracy
- Classification accuracy
- Decoy versus threat discrimination accuracy, and effectors spent on decoys
- Classifier **calibration**, not just accuracy. Scenarios Q to U exist to detect
  a model that has merely learned "turning means threat". A confident wrong answer
  on scenario Q is a worse failure than an uncertain right one on scenario P.
- False-positive rate
- Missed-track rate
- Track fragmentation
- Sensor-to-track latency
- Sensor-to-decision latency
- Sensor-to-simulated-defeat latency
- Throughput under increasing simultaneous UAS count

See `data/synthetic/README.md` for the on-disk format and generation contract.

## Open questions to settle before M4

1. ~~Distribution or single classification?~~ **Settled: distribution**, with
   control evidence held separately from identity. See the architecture document.
2. Is time simulated or real during benchmarks? Both are needed, and mixing them
   silently would corrupt every latency number.
3. ~~What is the authorisation policy model?~~ **Settled: hybrid.** Per-track
   state always exists; groups are additive. Modes A to D in the architecture
   document are all supported. Grouping is measured, not assumed.
4. How much observation history is needed before manoeuvre detection is
   trustworthy? This sets the floor on identification latency and therefore on
   total sensor-to-defeat latency.
