# DroneWatch V0.2 — architecture and domain model

Companion to [`V0.2_PANOPTES_ROADMAP.md`](V0.2_PANOPTES_ROADMAP.md). This
document proposes the smallest evolutionary structure that reaches the V0.2
capability set without rewriting V0.1.

## Guiding constraints

1. V0.1 functionality is preserved. Viso ingestion keeps working and becomes one
   sensor adapter among several rather than the architecture itself.
2. The frontend stays frozen until M10. Therefore `/api/events` must keep
   returning exactly what it returns today, as a projection over the new model.
3. No enterprise abstraction for its own sake. No dependency-injection
   framework, no message broker, no ORM until something concrete demands one.
4. Everything runs from synthetic data with no external service.

## Proposed layout

```
main.py                     # thin ASGI entrypoint; `uvicorn main:app` unchanged
benchmark.py                # swarm/saturation harness (M9)
dronewatch/
    domain/                 # dataclasses and enums only; no I/O, no framework
    sensors/                # adapters: base, viso, synthetic  (inbound edge)
    fusion/                 # association + track manager
    threats/                # assessment + prioritisation
    decisions/              # defeat-chain state machine, authorisation, audit
    effectors/              # abstract simulated effectors + assignment
    simulation/             # scenario runner, clock abstraction
    synthetic/              # seeded scenario generators
    metrics/                # latency ledger aggregation, derived metrics
    storage/                # repositories; SQLite today, swappable later
    api/                    # v1 compatibility router + v2 router
    interop/sapient/        # translation adapter (M11)
docs/
data/synthetic/
tests/
```

`main.py` remains at the repository root and remains the ASGI entrypoint, so the
documented start command, the CI invocation and the frozen dashboard's
same-origin assumptions all keep working. It shrinks to app construction and
router mounting.

### Dependency direction

`domain` depends on nothing. Everything depends inward toward `domain`. The
inbound edge (`sensors`) and the outbound edge (`api`, `interop`) are the only
places that know about wire formats. This is what makes SAPIENT an adapter
rather than a rewrite.

## Ratified architectural decisions

Decided 9 September 2026. These are settled; later work implements them rather
than revisiting them.

### Decision 1 — classification is a probability distribution

A track carries a distribution over apparent object classes, never a single
categorical label.

```
classification_distribution:
    THREAT:    0.62
    DECOY:     0.27
    BENIGN:    0.06
    FRIENDLY:  0.00
    UNKNOWN:   0.05
```

A derived `top_class` and `top_probability` may exist for display convenience.
They must never replace or shadow the distribution in storage, in the API, or in
any reasoning stage. Normalisation is explicit and tested rather than assumed.

`UNKNOWN` is always available and carries the mass when evidence is insufficient.
A track with no usable evidence is `UNKNOWN: 1.0`, not a low-confidence guess.

### Decision 2 — control evidence is separate from identity

Evidence that something is being actively flown is **not** a class label. It is a
separate set of track-level motion features:

```
active_control_probability   0..1, or absent
manoeuvre_score              0..1, or absent
motion_model_residual        >= 0, or absent
trajectory_confidence        0..1, or absent
```

Threat assessment may consume these features. It must not treat them as identity.
Two rules hold permanently:

```
ACTIVE MANOEUVRE  !=  THREAT
STRAIGHT FLIGHT   !=  DECOY
```

The system should infer evidence of agency and control without hard-coding that
evidence as identity. A classifier that has merely learned "turning means threat"
is a failure, and the synthetic counterexamples exist to detect exactly that.

### Decision 3 — hybrid authorisation

Every track always retains its own threat assessment, engagement state,
authorisation history, simulated outcome and audit trail. Tracks may in addition
belong to a `ThreatGroup`.

Four authorisation modes must all be representable:

| Mode | Meaning |
|---|---|
| A | Per-track authorisation |
| B | Group-level authorisation |
| C | Group authorisation with named individual exclusions |
| D | Per-track decision overriding a group decision |

Group authorisation is **not assumed to be better**. It trades operator decision
count against precision, and the benchmark exists to measure that trade rather
than to confirm a preference.

A group authorisation records exactly which track identifiers it covers. Coverage
is explicit and enumerable, never implied by group membership at read time, since
membership can change after the decision was made.

### Decision 4 — six concepts stay separate

These must never collapse into a single hostile boolean:

| Concept | Question it answers |
|---|---|
| Object / track identity | What does it appear to be? |
| Active-control / manoeuvre evidence | Does its motion suggest controlled behaviour? |
| Threat assessment | Does it present a defensive threat? |
| Engagement decision | What does the simulated system recommend? |
| Authorisation | Is the simulated action permitted? |
| Effector outcome | What was the simulated result? |

Each is a distinct type with its own lifecycle and its own audit entry. A test
enforces that reaching a simulated engagement requires an authorisation record,
because that is the one boundary where collapsing the concepts would matter most.

Note on naming: `ObjectClass.THREAT` means "appears to be a threat-type object".
It is an identity hypothesis, not a threat assessment. The assessment stage is
separate and may disagree with the distribution.

## Domain model

### SensorObservation

The atomic input. One sensor's statement about something it saw at a moment.

```
observation_id      ULID
sensor_id           str
modality            RADAR | RF | EO | IR | ACOUSTIC | VISUAL_FILE | OTHER
observed_at         datetime   # when the sensor says it saw it
received_at         datetime   # when we actually got it  (never sender-controlled)
position            Position | None
kinematics          Kinematics | None
classification      list[ClassificationHypothesis]
confidence          float 0..1 | None
signals             list[SignalFeature]      # RF
associated_ids      list[str]                # sensor-asserted association
raw                 dict                     # verbatim payload, always retained
quality             QualityFlags
```

Two properties carried over from V0.1.1 deliberately. `received_at` is ours, not
the sender's, which is the V0.1.1 timestamp fix generalised. `confidence` is
either a real 0 to 1 value or `None`; there is no fabricated middle.

`Position` is a tagged union rather than a lat/lon pair, because V0.1 already
proved that sensors supply frame coordinates, qualitative text, range-bearing,
or nothing at all. Forcing a single representation would invent precision.

### TrackCandidate

A hypothesis that an observation belongs to a track. Kept as an explicit type so
association decisions are inspectable and testable rather than buried in a loop.

### FusedTrack

```
track_id            ULID
state               TrackState
observations        list[SensorObservation]
contributing        set[sensor_id]
classification      ClassificationDistribution       # never a scalar label
motion              MotionEvidence                   # control evidence, NOT identity
confidence          float 0..1
uncertainty         Uncertainty
group_id            str | None                       # ThreatGroup membership
first_seen          datetime
last_seen           datetime
history             list[Position]
zone_relationship   OUTSIDE | APPROACHING | INSIDE | UNKNOWN
threat              ThreatAssessment | None
engagement          EngagementRecord | None
latency             LatencyLedger
```

### Two state machines, not one

The original sketch mixed track lifecycle with engagement lifecycle in a single
sequence. Splitting them is a genuine improvement, because a track can be
reacquired while an engagement is pending, and an engagement can fail while the
track continues. One combined enum cannot express that without illegal states.

```
TrackState:      TENTATIVE → CONFIRMED → CLASSIFIED → ASSESSED
                 with LOST, REACQUIRED, CLOSED reachable from most states

EngagementState: NONE → RECOMMENDED → DECISION_PENDING
                 → AUTHORISED | REJECTED
                 → EFFECTOR_ASSIGNED → ENGAGEMENT_PENDING → SIMULATED_ENGAGEMENT
                 → DEFEAT_CONFIRMED | DEFEAT_UNCONFIRMED
                 → RE_ENGAGEMENT_REQUIRED (loops back) | CLOSED
```

The authorisation boundary sits on exactly one transition,
`DECISION_PENDING → AUTHORISED`. Everything before it may be automatic.
Nothing after it may occur without a recorded decision. A test should assert
that no path reaches `SIMULATED_ENGAGEMENT` without an authorisation record.

### ThreatGroup and authorisation

A `ThreatGroup` collects tracks that an operator may reason about as one object.
Membership is advisory; authorisation coverage is not. A `GroupAuthorisation`
freezes the covered track identifiers at decision time and carries an explicit
exclusion set, so modes B, C and D of Decision 3 are all representable without
re-deriving membership later.

A per-track authorisation always wins over a group authorisation covering the
same track. That ordering is what makes mode D work, and it is tested.

### ThreatAssessment

Carries a score, a band, and a list of stated reasons with the evidence each rests
on. A score without a rationale is not usable in an audit, and PANOPTES is
explicitly about operator trust under load.

#### Decoy versus threat discrimination

A working hypothesis worth building the model around, because it bears directly
on effector exhaustion under saturation:

```
DECOY:   trajectory ≈ deterministic dynamics + environmental noise
THREAT:  trajectory ≈ controlled dynamics + manoeuvre process + environmental noise
```

The discriminating signal is the presence of a **manoeuvre process**: control
input that is not explainable as zero-mean environmental disturbance. A decoy
follows a fixed dynamics model perturbed by wind and sensor noise. A threat is
actively flown, so its trajectory carries structured, non-zero-mean deviations.

This matters operationally. Cheap decoys are a saturation tactic precisely
because they consume finite effectors. A system that cannot separate the two
exhausts its magazine on the decoys, which is the failure mode PANOPTES names.

Implementation consequence. Once tracks are filtered (M4), the natural place to
detect a manoeuvre process is the **innovation sequence**: the residual between
predicted and observed position. Under a correct constant-dynamics model with
zero-mean noise, innovations are zero-mean and serially uncorrelated. Sustained,
correlated, or non-zero-mean innovations indicate control input. That gives a
discriminator that is computable from what the tracker already produces, rather
than requiring a new sensor.

Three cautions, recorded now so they are not discovered late:

1. This is a **hypothesis, not a validated result**. It must be evaluated against
   synthetic scenarios before any confidence number derived from it is shown to
   an operator.
2. Manoeuvre detection needs observation history, so it is unavailable early in a
   track's life. The assessment must degrade to `UNKNOWN` rather than defaulting
   to decoy, since assuming decoy is the dangerous error.
3. A sophisticated decoy could fly a programmed manoeuvre, and a threat could fly
   straight. The discriminator raises the cost of deception; it does not settle
   identity, and must never be presented as though it does.

The ground-truth rule applies with full force here. The generator knows which
entity is a decoy. The classifier must never see that field.

### EngagementRecord and audit

The audit trail preserves what the system believed, its confidence, the
contributing evidence, the recommendation, the timestamp, who or what decided,
and the simulated outcome. Audit records are append-only.

## Latency instrumentation

`LatencyLedger` is built in M1, not late, because retrofitting stage timestamps
is far more expensive than stamping as you go.

Stages stamped: `first_sensor_observation`, `detection_created`,
`track_established`, `classification_available`, `threat_assessed`,
`decision_recommended`, `authorisation`, `effector_assignment`,
`simulated_engagement`, `simulated_defeat_assessment`.

Derived: detection, track, identification, assessment, decision, human, handoff,
simulated engagement, and total sensor-to-defeat latency.

Two rules that prevent meaningless numbers:

- Durations are computed from a monotonic source; wall-clock is recorded
  separately for display. Mixing them produces negative latencies under clock
  adjustment.
- The clock is injectable. Benchmarks run on simulated time; live operation runs
  on real time. A ledger records which clock produced it, because comparing the
  two is otherwise silently wrong.

## Swarm and saturation

Saturation is a design input, not a load test performed later.

- Ingestion is a bounded queue with explicit backpressure and a recorded drop
  policy. Silent unbounded growth would hide the exact failure PANOPTES cares about.
- Fusion runs on a tick over a batch, not per-observation, so cost scales with
  ticks rather than message count.
- Tracks cluster into groups so the operator sees a swarm as one decision object
  with members, not eighty rows.
- Authorisation supports group decisions, because per-track authorisation is the
  predicted bottleneck and measuring that is part of the point.
- Queue depth, decision backlog, and effector contention are exported as metrics
  from the start.

## Sensor abstraction

An adapter converts a wire format into `SensorObservation` and does nothing else.
It performs no fusion, no threat reasoning, and no storage.

```
class SensorAdapter(Protocol):
    modality: Modality
    def parse(self, payload: bytes | dict) -> list[SensorObservation]: ...
```

`viso.py` is the existing V0.1 normalisation moved behind this interface with its
behaviour unchanged, including the defensive rules that refuse to infer a
detection from narrative text or fabricate confidence. Those rules are reusable
across every adapter and are the most valuable code V0.1 produced.

## SAPIENT integration boundary

Investigated rather than assumed. Findings as of 9 September 2026:

- SAPIENT stands for Sensing for Asset Protection with Integrated Electronic
  Networked Technology, originating with Dstl.
- The Dstl Interface Control Document v7 has been **withdrawn in favour of
  BSI Flex 335**, which is the current specification. The standard document
  itself is obtained from BSI.
- Protobuf message definitions are published by Dstl at
  `github.com/dstl/SAPIENT-Proto-Files` under Apache 2.0, Crown copyright 2023,
  with directories for `bsi_flex_335_v1_0` and `bsi_flex_335_v2_0`.
- The envelope is `SapientMessage`, carrying `timestamp`, `node_id`,
  `destination_id`, and a `oneof` of `Registration`, `RegistrationAck`,
  `StatusReport`, `DetectionReport`, `Task`, `TaskAck`, `Alert`, `AlertAck`,
  and `Error`.
- `DetectionReport` carries `object_id`, `detection_confidence` documented as
  0 to 1, a repeated `classification` with per-class confidence and nested
  sub-classes, repeated `behaviour`, repeated `signal` for RF characteristics,
  `range_bearing` or `location`, velocity, predicted location, and
  `associated_detection` referencing detections from other nodes.

Consequences for our design, which is why this was worth checking:

1. The standard already assumes sensor nodes, a fusion node, and a GUI consumer.
   That is the shape we are building, so the adapter is translation, not a rewrite.
2. Classification as a repeated list with confidences confirms that our track
   classification should be a distribution rather than a scalar.
3. `associated_detection` means cross-sensor association is a first-class concept
   upstream of us, and our `SensorObservation.associated_ids` should preserve it.
4. Confidence on 0 to 1 matches V0.1.1 normalisation exactly. No conversion layer
   is needed, which is a small but real validation of the V0.1.1 fix.

Where the adapter sits: inbound at `dronewatch/interop/sapient/` producing
`SensorObservation`, and optionally outbound projecting `FusedTrack` into a
detection or alert message. Nothing else in the codebase should import protobuf.

**Claims discipline.** We have read the published message definitions. We have
not obtained or conformance-tested against BSI Flex 335 itself, and effector or
defeat semantics in the standard have not been verified. Until a conformance
test exists, the honest claim is "translates a subset of the published BSI Flex
335 v2.0 `DetectionReport`". Saying "SAPIENT compliant" would be false.

## Storage

SQLite remains. The `incidents` table stays as-is so V0.1 data and the frozen
dashboard keep working, and new tables are added alongside for observations,
tracks, assessments, engagements and audit records. A repository layer hides the
schema so the storage engine can change later without touching the domain.

The first index is likely needed when tracks are queried by state and last-seen.
There are currently no indexes at all, which is fine at V0.1 volumes and will
not be fine under swarm scenarios.

## API evolution

`/api/events` is frozen for compatibility and reimplemented as a projection over
the new model. New capability lands under `/api/v2/`: tracks, groups,
assessments, decisions, effectors, metrics, and audit. The dashboard migrates to
v2 at M10, not before.

## Testing strategy

- **Unit.** Pure domain logic, no I/O. Fast, the bulk of the suite.
- **Contract.** Each adapter against recorded fixtures, including the existing
  Viso payload shapes so V0.1 behaviour is pinned during the M3 move.
- **Scenario/golden.** Seeded synthetic scenarios with asserted outcomes.
- **Property.** Duplicate, delayed and out-of-order observations must not change
  the final track set. These are the cheapest high-value tests available.
- **Invariant.** No engagement without authorisation. No ground-truth import in
  evaluated modules. Both enforced by tests, not convention.
- **Regression.** The V0.1.1 suite is preserved unchanged as the compatibility floor.

## Benchmark strategy

`benchmark.py --scenario swarm --uas N` for N in 1, 10, 50, 100. Reports latency
percentiles per stage, throughput, queue depth, decision backlog and track
quality. Runs on simulated time with a fixed seed so runs are comparable.

Two hazards to avoid: measuring the harness rather than the system, and
optimising before the curve is understood. The deliverable at M9 is a curve, not
a speedup.

The comparison that matters is baseline workflow versus DroneWatch-assisted
workflow on the same seeded scenario. That requires modelling an unaided
operator, which is a genuine piece of work and should be scoped explicitly rather
than assumed.
